# Project Memory

Specification: [DESIGN.md](../documentation/DESIGN.md) (root system design) and [DESIGN.md](DESIGN.md) (this project's requirements and use cases, UC1-UC16).

- This project is the Svelte + TypeScript management UI.
- The API defaults to `http://127.0.0.1:5080`; override it with `VITE_API_BASE_URL`.
- Authentication uses the API's JWT token and local storage.
- The UI supports English and Dutch and remembers the selected language.
- Never hardcode user-facing labels in views/components; add them to `src/lib/i18n.ts` for every language instead (see [CLAUDE.md](CLAUDE.md)).
- Date-only values must be displayed with local calendar semantics; use the shared date utility.
- Main management areas are overview, matches, competitions, participants, categories, templates, accounts (UC16), profile (UC14), and tenant administration/sub-tenants (UC15).
- Accounts management (UC16) is tenant-administrator only: list shows username/real name/authorization, edit screen changes username, real name, e-mail, password (only if non-empty) and authorization; a user cannot change their own authorization. Backed by `GET/PUT /api/accounts/{id}`; `PUT` enforces the same username-required/username-uniqueness checks as `POST` (excluding the account's own id), surfaced via `error_USERNAME_REQUIRED`/`error_USERNAME_TAKEN`. "Add account" only asks for a username and creates an unprivileged (`Viewer`) account via `POST /api/accounts` (server generates a random initial password); on failure the add-form stays open with a coded error message.
- API errors that the UI must react to specifically (login, change-password, account creation) come back as `{ code, message }` instead of plain text. `api.ts`'s `ApiRequestError` carries `code`; never show the raw `message` to users. Use `labelForError(error, labels, fallbackKey)` from `src/lib/errors.ts`, which looks up an `error_<CODE>` key in `i18n.ts` (add one per language) and falls back to `fallbackKey` for unknown/network errors. Extend this pattern (`ApiError`/`error_<CODE>` keys) whenever a new endpoint's failures need specific UI messaging.
- The header shows the active tenant's own name/logo (falling back to the default "Centaur Scores" branding) and a profile button/avatar next to log out.
- Sub-tenant logos are uploaded client-side (SVG/PNG, 1:1 preferred aspect ratio, 256KB max) and stored as data URLs via the API; the `tenants.logo_url` column is `longtext`.
- Category management (UC5) and participant list management (UC7) each have dedicated list/detail views (`CategoriesView`/`CategoryDetailView`, `ParticipantListsView`/`ParticipantListDetailView`/`ParticipantMemberView`).
- Match template management (UC6, `TemplatesView`/`TemplateEditView`) was the last generic-stub section; the old `ManagementView.svelte`/`managementData.ts` generic fallback has been removed entirely now that all four tenant-home sections (participants, categories, templates, accounts) have dedicated screens.
- `MatchTemplate.configurationJson` is a free-form JSON blob the backend never parses/validates; its shape (`categoryOrder`, ordered `deviceNames`, `keyboard`, `disabledKeyRules`, `scoringRules`, `liveScopes`) is defined and owned entirely by the frontend in `src/lib/templateConfig.ts` (parse/default helpers) and `src/lib/types.ts` (`TemplateConfiguration` and friends). `TemplateEditView` manages standard device names and order; `MatchesView` creates those devices sequentially after creating a match from the template. Keyboard keys are `{ keyId, label, color, value }`, all fields required (the old delete/wipe key concept with nullable fields was removed; scorekeeper apps add their own delete key if needed). Keyboard keys can be reordered in `TemplateEditView`/`MatchMetadataEditView` via ▲/▼ move buttons. Scoring rules are an ordered list of `{ type: 'total' | 'countKey', keyId? }` tie-breakers. Live scopes mirror the real `LiveScoreScope` entity's fields.
- Categories and participant lists (with members) are eager-loaded in `App.svelte`'s `loadData()` alongside matches/competitions, since the backend already returns nested values/members in one call; after any mutation, call `refreshCategories()`/`refreshParticipantLists()`/`refreshTemplates()` to refetch rather than mutating local state.
- Participant list members have a per-member `isActive` flag (UC7); inactive members/lists are tagged and sorted after active ones. Every defined category must have a selected value before a member can be saved.
- Match management (UC8, `MatchesView`/`MatchDetailView`/`MatchMetadataEditView`/`MatchDevicesView`/`MatchParticipantView`/`MatchQrCodesView`) reuses the template config split: `Match.keyboardJson` holds `{ categoryOrder, keyboard, disabledKeyRules }` and `Match.scoringRulesJson` holds the ordered `ScoringRule[]` (see `src/lib/matchConfig.ts`); live scopes are real `LiveScoreScope` rows on the match, unlike the template's JSON blob.
- **Participant selection is a per-match/per-template concept, not per-device.** `Match`/`MatchTemplate` both carry `participantListId` (nullable — which participant list a match/template draws from) and `deviceSelectionMode: 'restricted' | 'list' | 'list-and-free'` (which participants a scoring device may choose between at score-entry time: only already-added match participants / freely from the list / list + already-added + free entry). `ScoreDevice` itself is now just `{ id, matchId, name }` — no mode, no participant-order JSON; `MatchDevicesView` is just a name-only add/remove list. `Match.allowFreeParticipants` controls whether ad-hoc (non-list) participants can be added to the match at all.
- Once a match has any participants, its `participantListId` is locked (edit UI disables the select and shows `participantListLockedHint`; backend returns 409 `PARTICIPANT_LIST_LOCKED` if you try to change it anyway via `PUT /api/matches/{id}`).
- **Universal list-rendering rule**: whenever showing a participant-list member for selection (add-participant dropdowns, etc.), always render "full name (concatenated category values)" using the full tenant `categories` list (not a match/template's restricted `categoryOrder`), and always exclude members with `isActive === false` from selection dropdowns — this is a general rule stated by the user, not scoped to one screen.
- `MatchDetailView`'s add-participant form no longer lets the user pick a source list — the source list is fixed to `match.participantListId`; the add-mode (list vs. manual) is derived automatically from whether a source list exists and `match.allowFreeParticipants`.
- "Add match" only asks for name/date/optional template; ends/arrowsPerEnd default to 10/3 (templates don't define them) and are editable afterwards in `MatchMetadataEditView`. Choosing a template copies its keyboard/rules/live-scopes onto the new match and opens the match home directly; no template opens `MatchMetadataEditView` for ad-hoc setup instead.
- The match home screen (`MatchDetailView`) is participant-list-first per UC8, with sort (name/score) and group (none/category/device) toggles, inline add-participant (from any participant list, or manual entry when `allowFreeParticipants`), and function buttons for metadata/devices/QR codes/CSV export/results-per-scope/delete (confirmed). A results scope opens the anonymous `/narrowcast/{scope}` display (no tenant in the URL — it rotates through live matches from *every* tenant that has an open match using that scope name), which rotates through data from `/live-scoring/match/{scope}` and `/live-scoring/match/{scope}/{matchId}`.
- The printable QR codes screen (`MatchQrCodesView`, route `/matches/{id}/qr`) renders without the app header, 4 bordered blocks per printed page, each with the match name, device name, and a QR code (via the `qrcode` npm package) encoding `${apiBase}/scorekeeper/{tenantId}/{matchId}/{deviceId}` — this endpoint already exists unauthenticated in `PublicScoresController`.
- A participant's assigned score device is set via `PUT /api/matches/{id}/participants/{participantId}/device` (added for UC8); assigning clears the participant from every other device's restricted participant list, matching the "one device per participant" rule in the root DESIGN.md.
- `MatchParticipantView` lets managers edit a match participant's metadata in place (`PUT /api/matches/{id}/participants/{participantId}`, reuses `CreateMatchParticipantRequest`'s shape) — either manually (lastName/fullName/federationNumber/categories) or by "replacing" the participant with another member from the match's source `participantListId` (excludes members already assigned elsewhere in the match and inactive members, per the universal list-rendering rule above). The update response doesn't include `scores`, so the frontend merges only the metadata fields locally and keeps existing scores until the next full refresh. Requires passing `participantLists` into `MatchParticipantView` (from `App.svelte`).
- Score entry (`setScore`) and quick-set-total (`applyQuickSet`) in `MatchParticipantView` optimistically reassign the local `participant` prop with the new/replaced scores before awaiting the API calls, so totals/running totals/dropdown selections update immediately instead of waiting on the full match refresh; `onChanged()` is still awaited afterwards to reconcile with the server.
- Known UC8 gaps (backend has no support, intentionally not implemented): assigning arbitrary accounts as "match admins" — there's no such entity/endpoint yet.
- UI tests use Vitest; type checking uses `svelte-check`.
- Run `npm test`, `npm run check`, and `npm run build` after frontend changes (also documented in CLAUDE.md).
- `Match.participantCount` was a dead frontend-only field the API never populated (a stray `participant_count` DB column was even dropped from the API's `matches` table as unrelated cruft — see `RemoveStrayMatchParticipantCountColumn` migration). Both `GET /api/matches` and `GET /api/matches/{id}` already eager-load and serialize the full `Participants` collection per match, so `matchParticipantCount(match)`/`matchUnlistedParticipantCount(match)` in `src/lib/matchParticipants.ts` just derive counts from `match.participants` client-side (length, and members without a `participantListMemberId` for manually-added/free entries) — no backend change was needed. `MatchesView`'s full list surfaces a red "N unlisted" indicator next to the count as an operator trigger-to-act; `HomeView`'s open-matches panel only shows the corrected total.
- Participant list Excel export/import (`ParticipantListDetailView`) is generated/parsed entirely server-side (`GET /api/participant-lists/{id}/export.xlsx?language=`, `POST .../import.xlsx`) — the frontend just triggers a blob download (mirrors `downloadMatchExport`) and posts a `FormData` upload (`api.importParticipantList`), and shows the returned `{ created, updated, warnings }` summary. Both buttons are gated on a new `canManage` prop (`isAdmin || authorization === 'Manager'`, computed once in `App.svelte` and passed down) since export/import — like every other write on this screen — is a manager-or-higher action; unlike other manage actions in this codebase (which just rely on the backend's 403), this pair is deliberately hidden from viewers in the UI too, per explicit instruction. Coded import failures reuse `labelForError` with `error_IMPORT_*` keys (`IMPORT_MISSING_SHEET`, `IMPORT_UNRECOGNIZED_HEADERS`, `IMPORT_INVALID_FILE`, `IMPORT_FILE_MISSING`).
- All list-row/nav "navigate to a child view" controls (matches, competitions, participant lists/members, tenants, accounts, categories, templates, home dashboard, header nav, and the match QR-codes/results actions that used to call `window.open`) were converted from `<button on:click>` to `<a href>` so right-click/middle-click/ctrl-click can open the target in a new tab — see the "Navigation to another route" convention in CLAUDE.md. `router.ts` gained one path-builder function per route (`matchPath`, `competitionPath`, `participantMemberPath`, `matchResultsPath`, etc., used by both `App.svelte` and the view components) and a `navigateOnClick(event, action)` helper (plain left click → `preventDefault()` + run the existing SPA `navigate()` callback; modifier/middle click → let the browser open the `href` natively in a new tab, which does a normal fresh page load there — same-tab clicks stay reload-free). `app.scss` got a global `a { text-decoration: none; color: inherit; }` reset plus `a` variants added next to a few tag-qualified `button` selectors (`nav button`, `.quick-links button`) so the converted anchors keep the exact prior look. Found but deliberately left alone: `App.svelte`'s `signIn()` calls `navigate('/')` only after `loadData()` resolves, so a very fast click during that window can get clobbered by that trailing redirect — a pre-existing race, not reachable by a human clicking normally, unrelated to this change.
- The home screen's bottom nav (`HomeView.svelte`'s old plain `.quick-links` buttons for participants/categories/templates/accounts/tenants/backup-restore/personal-best) was converted to the same icon+title+description tile pattern used by `BackupRestoreView`/`PersonalBestView` (`.pb-tile-grid`/`.pb-tile`/`.pb-tile-icon`/`.pb-tile-title`/`.pb-tile-description`). Those classes were previously duplicated as component-local `<style>` blocks in both those views; they're now hoisted into `app.scss` as shared global classes (`.quick-links` CSS was removed entirely) — reuse `.pb-tile-grid`/`.pb-tile` for any future icon-tile action grid instead of redefining it locally. `HomeView`'s `quickLinks` prop changed shape from `[path, label][]` to `{ path, icon, title, description }[]`; `App.svelte`'s `homeQuickLinks` builds it in a fixed order (categories, participants, templates, personal-best if visible, then admin-only accounts/tenants/backup-restore) with icons as emoji and new `homeTile*Title`/`homeTile*Description` i18n keys (some tiles reuse existing title keys like `t.categories`/`t.accounts`, others — participants/templates — got dedicated `homeTileParticipantsTitle`/`homeTileTemplatesTitle` because the tile wants a different label than that view's own page-header title).
- **Tenant-less login + multi-tenant access resolution (2026-08-29)**: `LoginView` no longer has a tenant dropdown (`login(username, password)` in `api.ts` dropped the `tenantId` param, and `fetchTenants()`/the `tenants` store in `data.ts` were removed with it). The API's login token now starts with an empty tenant claim; `App.svelte`'s `bootstrapSession()` (replacing the old `loadData()` wrapper, called from both `signIn()` and `onMount()`) fetches `GET /api/auth/me` first — via the new standalone `loadProfile(api)` in `data.ts`, split out of the eager-load batch specifically so it runs *before* every other tenant-scoped call, which now 403s (`TENANT_NOT_SELECTED`) without a resolved tenant — reads its `authorizedForTenants: TenantAccess[]` (home tenant + every hierarchy descendant, all at the account's own level), resolves one via `resolveTenantSelection()` (single tenant auto-selects; else a `localStorage['centaur-tenant']` hint if still valid; else alphabetically-first by name), and calls `api.selectTenant(tenantId)` to re-mint the token before running the rest of `loadData()`. Zero authorized tenants renders `NoTenantAccessView` (full-screen error + logout, gated by a new `tenantAccessError` flag); a `sessionReady` flag gates the full app-shell render so nothing tenant-scoped renders before `bootstrapSession()` finishes. `localStorage['centaur-tenant']` was repurposed from "login-form pre-selection" to "last-selected-tenant hint" — it's now written only once a tenant is actually resolved (never in `signIn()` itself) and deliberately never cleared on `signOut()`, so it survives to the next login. `bootstrapSession()` always calls `selectTenant()` even when the stored token already has a valid tenant — a deliberate one-round-trip cost for a single code path that also self-heals if the account's tenant tree changed since the token was minted. The header's profile menu gets a "Switch to a different tenant" item (`AppHeader`'s new `showTenantSwitch` prop, true when `authorizedForTenants.length > 1`) linking to a new `SelectTenantView` (`/select-tenant` route) showing one `.pb-tile` per tenant sorted alphabetically with logo + level, which calls `api.selectTenant` via an `onSelectTenant` callback owned by `App.svelte` (not a local API call, since a successful switch must mutate `App.svelte`'s top-level `token`/`tenant` state — the one documented exception to this codebase's usual "view calls `api.x()` then `onChanged()`" convention). The small `authorizationLabel()` helper, previously duplicated locally in `AccountsView.svelte`, was extracted to `src/lib/authorization.ts` for `SelectTenantView` to reuse.
- **Tenant-level default narrowcast scope + "claim scope" (2026-08-29)**: the tenant's effective default scope (`DefaultScopeSettings.effectiveValue` from `GET /api/tenants/current/default-scope`, resolved server-side up the tenant hierarchy) is loaded once into the `defaultScopeSettings` store in `data.ts` alongside `currentTenant`/etc. in `loadData()`, and derived in `App.svelte` as `effectiveDefaultNarrowcastScope` — passed down to `MatchesView` (the no-template "add match" fallback scope) and `TemplatesView` (new-template default via `buildEmptyTemplateConfiguration(defaultScope)`, replacing the old hardcoded `'all'`/`emptyTemplateConfiguration` constant — that constant still exists calling `buildEmptyTemplateConfiguration()` with no arg for the parse-failure fallback in `parseTemplateConfiguration`, where a fixed `'all'` is fine since that path is corrupt-JSON recovery, not new-template UX). Editing the tenant's own override lives in a new self-service `TenantSettingsView`/`tenant-settings` route (home tile gated on `canManage`, not `isAdmin` — distinct from the existing admin-only `TenantsView`/`TenantEditView`, which manage *child* tenants and also gained a `defaultNarrowcastScope` field for administrators to override on a sub-tenant). `MatchDetailView` reactively calls `api.fetchScopeConflicts(match.id)` whenever `match` changes (mirrors the existing `$: if (match.id) loadResults()` pattern — Svelte reactive statements re-run on *reassignment* of a referenced prop, not on its value changing, so this refires correctly after activate/deactivate even though `match.id` itself never changes) and, if any conflicts come back, shows a warning box (reusing the `#fdeeea`/`#e8755b` tint already used for `.unlisted-row` in the same file) listing each colliding tenant/scope/count with a "claim scope" button (`api.claimScope`) that re-checks conflicts afterward.
