# Project Memory

Specification: [DESIGN.md](../documentation/DESIGN.md) (root system design) and [DESIGN.md](DESIGN.md) (this project's requirements and use cases, UC1-UC16).

- This project is the Svelte + TypeScript management UI.
- The API defaults to `http://127.0.0.1:5080`; override it with `VITE_API_BASE_URL`.
- Authentication uses the API's JWT token and local storage.
- The UI supports English and Dutch and remembers the selected language.
- Never hardcode user-facing labels in views/components; add them to `src/lib/i18n.ts` for every language instead (see [COPILOT.md](COPILOT.md)).
- Date-only values must be displayed with local calendar semantics; use the shared date utility.
- Main management areas are overview, matches, competitions, participants, categories, templates, accounts (UC16), profile (UC14), and tenant administration/sub-tenants (UC15).
- Accounts management (UC16) is tenant-administrator only: list shows username/real name/authorization, edit screen changes real name, e-mail, password (only if non-empty) and authorization; a user cannot change their own authorization. Backed by `GET/PUT /api/accounts/{id}`. "Add account" only asks for a username and creates an unprivileged (`Viewer`) account via `POST /api/accounts` (server generates a random initial password); on failure the add-form stays open with a coded error message.
- API errors that the UI must react to specifically (login, change-password, account creation) come back as `{ code, message }` instead of plain text. `api.ts`'s `ApiRequestError` carries `code`; never show the raw `message` to users. Use `labelForError(error, labels, fallbackKey)` from `src/lib/errors.ts`, which looks up an `error_<CODE>` key in `i18n.ts` (add one per language) and falls back to `fallbackKey` for unknown/network errors. Extend this pattern (`ApiError`/`error_<CODE>` keys) whenever a new endpoint's failures need specific UI messaging.
- The header shows the active tenant's own name/logo (falling back to the default "Centaur Scores" branding) and a profile button/avatar next to log out.
- Sub-tenant logos are uploaded client-side (SVG/PNG, 1:1 preferred aspect ratio, 256KB max) and stored as data URLs via the API; the `tenants.logo_url` column is `longtext`.
- Category management (UC5) and participant list management (UC7) each have dedicated list/detail views (`CategoriesView`/`CategoryDetailView`, `ParticipantListsView`/`ParticipantListDetailView`/`ParticipantMemberView`).
- Match template management (UC6, `TemplatesView`/`TemplateEditView`) was the last generic-stub section; the old `ManagementView.svelte`/`managementData.ts` generic fallback has been removed entirely now that all four tenant-home sections (participants, categories, templates, accounts) have dedicated screens.
- `MatchTemplate.configurationJson` is a free-form JSON blob the backend never parses/validates; its shape (`categoryOrder`, ordered `deviceNames`, `keyboard`, `disabledKeyRules`, `scoringRules`, `liveScopes`) is defined and owned entirely by the frontend in `src/lib/templateConfig.ts` (parse/default helpers) and `src/lib/types.ts` (`TemplateConfiguration` and friends). `TemplateEditView` manages standard device names and order; `MatchesView` creates those devices sequentially after creating a match from the template. Keyboard keys are `{ keyId, label, color, value }`, all fields required (the old delete/wipe key concept with nullable fields was removed; scorekeeper apps add their own delete key if needed). Keyboard keys can be reordered in `TemplateEditView`/`MatchMetadataEditView` via ▲/▼ move buttons. Scoring rules are an ordered list of `{ type: 'total' | 'countKey', keyId? }` tie-breakers. Live scopes mirror the real `LiveScoreScope` entity's fields.
- Categories and participant lists (with members) are eager-loaded in `App.svelte`'s `loadData()` alongside matches/competitions, since the backend already returns nested values/members in one call; after any mutation, call `refreshCategories()`/`refreshParticipantLists()`/`refreshTemplates()` to refetch rather than mutating local state.
- Participant list members have a per-member `isActive` flag (UC7); inactive members/lists are tagged and sorted after active ones. Every defined category must have a selected value before a member can be saved.
- Match management (UC8, `MatchesView`/`MatchDetailView`/`MatchMetadataEditView`/`MatchDevicesView`/`MatchParticipantView`/`MatchQrCodesView`) reuses the template config split: `Match.keyboardJson` holds `{ categoryOrder, keyboard, disabledKeyRules }` and `Match.scoringRulesJson` holds the ordered `ScoringRule[]` (see `src/lib/matchConfig.ts`); live scopes are real `LiveScoreScope` rows on the match, unlike the template's JSON blob.
- **Participant selection is a per-match/per-template concept, not per-device.** `Match`/`MatchTemplate` both carry `participantListId` (nullable — which participant list a match/template draws from) and `deviceSelectionMode: 'restricted' | 'list' | 'list-and-free'` (which participants a scoring device may choose between at score-entry time: only already-added match participants / freely from the list / list + already-added + free entry). `ScoreDevice` itself is now just `{ id, matchId, name }` — no mode, no participant-order JSON; `MatchDevicesView` is just a name-only add/remove list. `Match.allowFreeParticipants` controls whether ad-hoc (non-list) participants can be added to the match at all.
- Once a match has any participants, its `participantListId` is locked (edit UI disables the select and shows `participantListLockedHint`; backend returns 409 `PARTICIPANT_LIST_LOCKED` if you try to change it anyway via `PUT /api/matches/{id}`).
- **Universal list-rendering rule**: whenever showing a participant-list member for selection (add-participant dropdowns, etc.), always render "full name (concatenated category values)" using the full tenant `categories` list (not a match/template's restricted `categoryOrder`), and always exclude members with `isActive === false` from selection dropdowns — this is a general rule stated by the user, not scoped to one screen.
- `MatchDetailView`'s add-participant form no longer lets the user pick a source list — the source list is fixed to `match.participantListId`; the add-mode (list vs. manual) is derived automatically from whether a source list exists and `match.allowFreeParticipants`.
- "Add match" only asks for name/date/optional template; ends/arrowsPerEnd default to 10/3 (templates don't define them) and are editable afterwards in `MatchMetadataEditView`. Choosing a template copies its keyboard/rules/live-scopes onto the new match and opens the match home directly; no template opens `MatchMetadataEditView` for ad-hoc setup instead.
- The match home screen (`MatchDetailView`) is participant-list-first per UC8, with sort (name/score) and group (none/category/device) toggles, inline add-participant (from any participant list, or manual entry when `allowFreeParticipants`), and function buttons for metadata/devices/QR codes/CSV export/results-per-scope/delete (confirmed). A results scope opens the anonymous `/narrowcast/{scope}` display (no tenant in the URL — it rotates through live matches from *every* tenant that has an open match using that scope name), which rotates through data from `/live-scoring/match/{scope}` and `/live-scoring/match/{scope}/{matchId}`.
- The printable QR codes screen (`MatchQrCodesView`, route `/matches/{id}/qr`) renders without the app header, 4 bordered blocks per printed page, each with the match name, device name, and a QR code (via the `qrcode` npm package) encoding `${apiBase}/scorekeeper/{tenantId}/{matchId}/{deviceId}` — this endpoint already exists unauthenticated in `PublicScoresController`.
- A participant's assigned score device is set via `PUT /api/matches/{id}/participants/{participantId}/device` (added for UC8); assigning clears the participant from every other device's restricted participant list, matching the "one device per participant" rule in the root DESIGN.md.
- `MatchParticipantView` lets managers edit a match participant's metadata in place (`PUT /api/matches/{id}/participants/{participantId}`, reuses `CreateMatchParticipantRequest`'s shape) — either manually (lastName/fullName/federationNumber/categories) or by "replacing" the participant with another member from the match's source `participantListId` (excludes members already assigned elsewhere in the match and inactive members, per the universal list-rendering rule above). The update response doesn't include `scores`, so the frontend merges only the metadata fields locally and keeps existing scores until the next full refresh. Requires passing `participantLists` into `MatchParticipantView` (from `App.svelte`).
- Score entry (`setScore`) and quick-set-total (`applyQuickSet`) in `MatchParticipantView` optimistically reassign the local `participant` prop with the new/replaced scores before awaiting the API calls, so totals/running totals/dropdown selections update immediately instead of waiting on the full match refresh; `onChanged()` is still awaited afterwards to reconcile with the server.
- Known UC8 gaps (backend has no support, intentionally not implemented): assigning arbitrary accounts as "match admins" — there's no such entity/endpoint yet.
- UI tests use Vitest; type checking uses `svelte-check`.
- Run `npm test`, `npm run check`, and `npm run build` after frontend changes (also documented in COPILOT.md).
