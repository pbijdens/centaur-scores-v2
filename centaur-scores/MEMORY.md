# Project Memory

Written in the same spirit as [CLAUDE.md](CLAUDE.md) but focused on decisions/gotchas discovered while building specific features, rather than the stable architectural facts CLAUDE.md documents.

- **`CLAUDE.md`'s Architecture section was badly stale until 2026-09-20** — it described a pre-QR-pairing, `/match/...`+`/devices/<deviceID>/sync` API (`MatchModel`, no `MatchRepository`/`ScorekeeperMatch`) that a much earlier branch (`flutter-new-api`, already merged into `main` long before this note) had already fully replaced with the QR-pairing + `/scorekeeper/{tenantId}/{matchId}/{deviceId}` API this app actually runs on today. Whoever wrote that section never updated it after the migration. Rewritten from a fresh read of the actual code (`app_navigator.dart`, `repository.dart`, `centaur_scores_api.dart`, `pairing_url_parser.dart`) rather than trusted as-is — if CLAUDE.md and the real code ever disagree again, trust the code and fix the doc, don't propagate the stale description forward.
- **Flutter Web cannot exercise this app's real network layer** — `CentaurScoresAPI._request` builds an `HttpClient`/`IOClient` from `dart:io`, which doesn't exist on web at all; every real request throws `Unsupported operation: Platform._version` at runtime (compiles fine, fails only when actually invoked). Confirmed via `flutter run -d web-server` + Playwright: the pairing *screen itself* renders and is fully interactive (CanvasKit renders to `<canvas>` with no real DOM — click the 1×1 `flt-semantics-placeholder` element via a dispatched `MouseEvent` to enable Flutter's accessibility/semantics tree, which then exposes real ARIA nodes including a hidden `<textarea>` that mirrors whatever on-canvas `TextField` currently has focus, and `[role="button"]` elements for buttons — click canvas coordinates first to focus a field, then `page.keyboard.type(...)`, then dispatch a click on the matching semantics button), but pairing itself always fails with the `Platform._version` error the moment it tries to actually fetch. No Linux desktop build toolchain (`clang`/`cmake`/`ninja-build`/`libgtk-3-dev`) is installed in this sandbox either, and no Android/iOS emulator is available. **Net effect: real end-to-end verification of anything that talks to the API needs a physical/emulated device outside this sandbox** — `flutter analyze` + `flutter test` + careful code review is the ceiling here. Keep this Playwright semantics-tree technique in mind if a future session needs to drive Flutter Web UI (even non-networked screens) for verification.
- **Scorecard signing (2026-09-20)** — see `../documentation/SIGNING-SCORECARDS.md` for the full cross-repo feature; this is the Flutter client phase (API + web-ui phases shipped first). `ScorekeeperMatch.signatureMode` and `ScorekeeperMatchParticipant.signed`/`signedAtUtc`/`archerSignatureDataUrl`/`markerSignatureDataUrl` are new fields with `@JsonKey(defaultValue: ...)` so a match cached locally before this update still parses instead of throwing `LateInitializationError` (falls back to `signatureMode: 'none'`/`signed: false`, i.e. "no signing UI" until the next successful poll refreshes it with real values). New `PendingSignatures`/`PendingSignature` models (hand-written JSON, `lib/src/model/pending_signatures.dart`) mirror `PendingUpdates`'s shape but hold no "old" conflict-detection value, since signing has no conflict resolution per the spec — `MatchRepository.flushPendingSignatures` just retries on the existing 8s timer until it lands, and specifically treats a `SCORECARD_SIGNED` `ApiException` as success (removes the pending entry) rather than a failure to keep retrying, since that response means the end state is already correct (e.g. a raced duplicate send, or the manager withdrew-then-someone-else-signed via the full API). Added a `_signaturesSyncing` guard (mirroring `flushPendingScores`' `_syncStatus == syncing` check) after realizing two `recordSignature` calls close together (e.g. signing two participants back-to-back) would otherwise both fire-and-forget their own `flushPendingSignatures()`, and a second overlapping flush snapshotting mid-flight could double-send an entry the first one was already landing — without the `SCORECARD_SIGNED`-is-success handling above, that would have gotten permanently stuck retrying every 8s forever.
- **UI (reworked 2026-09-24)**: the Sign button lives in `SingeParticipantFooter` (the totals row), in the same slot as the keypad's Next/Close buttons, and only shows while that column's keypad is closed (`ScoresViewmodel.isKeyboardVisibleFor` is the single source of truth for "keypad open" - it also returns false for a signed card, and for a fully-filled card awaiting signature, so completing the last arrow collapses the keypad and the Sign button appears in its place). `SignArea` below the keypad slot now only renders the signed state (signature thumbnails / read-only notice) and is empty otherwise; `startSigning()` in `sign_area.dart` opens the confirm/capture dialog. The earlier design (a separate always-visible Sign row that borrowed `_keyboardScrollKey` to scroll into view) was dropped at the user's request - it cost a whole row.
- **Layout budget**: `StyleHelper.preferredCellHeight` divides remaining vertical space (`screen height - scVerticalOverhead`) by the number of ends shown. It briefly reserved extra height for a Sign row (`includeSignArea`); removed again once the button moved into the footer.
- **Ink capture**: `signature_pad.dart` hand-rolls the drawing surface (`Listener` for raw pointer down/move/up/cancel → `SignaturePadController` accumulates `List<List<Offset>>` strokes → `CustomPainter` draws them) instead of adding a signature-pad package, per the cross-repo decision in `SIGNING-SCORECARDS.md` to keep this app's minimal-dependency posture (4 runtime deps before this feature, still 4 after). `SignaturePadController.toPngBytes()` exports via the wrapping `RepaintBoundary`'s `RenderRepaintBoundary.toImage()` + `toByteData(ImageByteFormat.png)` — the `RepaintBoundary`'s `Container(color: Colors.white)` background is what makes the exported PNG opaque white-backed rather than transparent, matching the "black and white low resolution drawing" storage convention from the spec. `SignatureCaptureDialog` lays out two of these stacked (`AspectRatio(aspectRatio: 5/1)` each, per the spec's split-screen sizing) inside a `Dialog.fullscreen`, requires both pads non-empty before confirming, and returns a `SignatureCaptureResult(archerDataUrl, markerDataUrl)` as base64 `data:image/png;base64,...` strings (popped via the real `Navigator`, not `AppNavigator`, since this is a transient modal action not a logical app screen).
- **Signature dialog must never scroll**: a `SingleChildScrollView` around the pads competes with the pads' `Listener` for vertical drags, so signing in landscape scrolled the page. `SignatureCaptureDialog` instead sizes both 5:1 pads with a `LayoutBuilder` to fit the remaining height (title + buttons share one top row to save space). The painter `clipRect`s to its size because a pointer that starts in the pad keeps delivering moves after leaving it.
- **Score card must listen to `MatchRepository` itself**: `ScoresView` builds `const ScoreEntryFullPageWidget()`, and a const widget is never rebuilt by `AppShell`'s `ListenableBuilder` (same canonicalization gotcha documented in `app_shell.dart`). Without its own `addListener`, a fresh signature or a server-side unsign only showed after navigating away and back. It also calls `fetchMatchInfo()` on open so server-side changes don't wait for the 60s poll.
- **Read-only lock**: once `participant.signed`, the numeric keypad can never reopen for them (`keyboard()`'s render gate checks `!participantModel.signed` regardless of `activeKeyboard`) and tapping any score cell is a no-op (`single_participant_score_form.dart`'s `onTapScoreField` early-returns on `_participant.signed`) — there was no locked/read-only concept anywhere in this app before this feature, so both of these are new protection, not an extension of a pre-existing pattern. There is no anonymous unsign in this app (or in the API for anonymous callers at all) — withdrawing a signature is manager-only, via the authenticated full API, never exposed to a scoring device.
