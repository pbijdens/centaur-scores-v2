# Project Memory

Specification: [DESIGN.md](../documentation/DESIGN.md)

- This project is the Centaur Scores .NET API.
- Runtime target is .NET 10.
- Persistence uses EF Core with MySQL through Pomelo.
- Database identifiers must remain lowercase.
- The configured development database is `centaurscores2`; credentials should move to environment configuration before deployment.
- Authentication uses JWT bearer tokens with tenant and account claims.
- Root development login is seeded by `DatabaseInitializer`.
- Business logic belongs in `Application`; HTTP endpoints belong in `Api/Controllers`.
- Respect `.editorconfig` for code style and formatting.
- Keep code clean and readable, with no multiple statements on a single line.
- Keep complex logic in application services instead of controllers.
- Add concise code comments for non-obvious logic and important design choices.
- Backend tests are in `CentaurScores.Api.Tests`.
- Match CSV export follows `Match.KeyboardJson` order: keyboard key-count columns, missing-arrow `Null`, grouped-end `SplitN` totals, category values in `categoryOrder`, then last name. Keyboard key labels and category names/values are used as CSV text.
- Client-actionable error responses (login, change-password, account creation) return a coded `ApiError { code, message }` body instead of a plain message, so the frontend can map `code` to a translated string. `message` is developer-facing only. See `Contracts.ApiError` and `API_ENDPOINTS.md` for the known codes; extend this pattern for new endpoints whose failures the UI needs to react to specifically.
- `ParticipantListMember` has an `IsActive` flag (default `true`); `CreateParticipantRequest.IsActive` defaults to `true` when omitted. Added via the `AddParticipantMemberIsActive` migration.
- `PublicScoresController` exposes unauthenticated `scorekeeper/{tenantId}/{matchId}/{deviceId}` (tenant-scoped), `live-scoring/match/{scope}`, and `live-scoring/match/{scope}/{matchId}` endpoints. Live scoring is deliberately *not* tenant-scoped: the list includes every open match (from any tenant) configured for the scope, and the detail response resolves its tenant from the match itself (`match.TenantId`), not from the route. The detail response is built by `LiveScoringService`.
- `PUT /api/matches/{id}/participants/{participantId}/device` assigns/unassigns a participant's score device with `{ deviceId }` (nullable); `ScoreDevice` no longer tracks per-device participant assignment (no `ParticipantOrderJson`) — the participant's own `DeviceId` is the single source of truth.
- `PUT /api/matches/{id}/participants/{participantId}` updates a match participant's metadata (`ParticipantListMemberId?`, `LastName`, `FullName`, `FederationNumber?`, `Categories`) reusing `CreateMatchParticipantRequest`; used by the frontend both for manual edits and for "replacing" a participant with a different source-list member. Returns 409 if the new `ParticipantListMemberId` is already assigned to a different participant in the match. Note the response doesn't eager-load `Scores` (not `.Include`d), matching the existing `AssignParticipantDevice` behavior.
- **Participant selection is per-match/per-template, not per-device.** `Match` and `MatchTemplate` both have `ParticipantListId` (nullable `Guid`) and `DeviceSelectionMode` (string: `restricted`/`list`/`list-and-free`, default `"restricted"`); `ScoreDevice` is now just `{ MatchId, Name }`. `MatchTemplate.AllowFreeParticipants` (bool) mirrors `Match.AllowFreeParticipants`.
- The anonymous scorekeeper API is implemented by `ScorekeeperService` and `PublicScoresController`. It returns typed device projections, enforces open-match/device/tenant scoping, supports participant assignment and optimistic score updates, and exposes participant options and UTC time under `/scorekeeper/{tenantId}/{matchId}/{deviceId}`. Scorekeeper calls are logged with the remote IP and route parameters.
- Changing a match's `ParticipantListId` via `PUT /api/matches/{id}` is rejected with 409 `ApiError("PARTICIPANT_LIST_LOCKED", ...)` once the match already has any `MatchParticipants` rows — the participant list is fixed once populated.
- **Schema-drift lesson (recurring bug class, hit 4 times this project: `logo_url`, `participant_count`, `round_count`, then avoided proactively for `device_selection_mode`)**: whenever an EF migration auto-generates `AddColumn<T>(..., nullable: false)` for a table that may already contain rows, always hand-edit the migration to add an explicit `defaultValue:` — otherwise `dotnet ef database update` succeeds (adds the column with no default) but the next `INSERT` that doesn't set that column fails at runtime with a DB-level "doesn't have a default value" error, not a migration-time error. Check every auto-generated non-nullable `AddColumn` migration for this before applying. Stray untracked columns left over from early prototyping (present in the DB but never modeled in `Domain.cs`/never migrated) hit this same failure mode on every insert into that table; fix by adding a migration that `DropColumn`s the stray column (see `RemoveStrayMatchParticipantCountColumn` and `RemoveStrayCompetitionRoundCountColumn`).
- **Model snapshot corruption lesson**: hand-writing migration `.cs` files without also running `dotnet ef migrations add`/updating `ApplicationDbContextModelSnapshot.cs` leaves the snapshot stale. The next real `dotnet ef migrations add` will then diff against the stale snapshot and either propose recreating/dropping unrelated tables/columns ("operation scaffolded that may result in loss of data") or, if the snapshot is fully empty, silently think there is nothing to migrate. Symptom seen: `ApplicationDbContextModelSnapshot.cs` had an entirely empty `BuildModel` body even though multiple entities/migrations existed. Fix used: temporarily comment out the new property, run `dotnet ef migrations add <Temp>` to regenerate an accurate snapshot reflecting the true deployed baseline, delete the temp migration's `.cs`/`.Designer.cs` (keep the regenerated snapshot), restore the property, then run `dotnet ef migrations add <RealName>` again to get a clean, minimal diff. Always verify with one more throwaway `migrations add` afterward that the resulting Up/Down is empty (proves model == snapshot) before removing it. When hand-authoring a migration going forward, immediately follow up by regenerating the snapshot the same way rather than skipping it.
- **Participant list Excel export/import (`IParticipantListExcelService`/`ParticipantListExcelService`, `ClosedXML` package) is the one place in the API concerned with translated text** — `ParticipantListExcelLabels.For(language)` holds the EN/NL pairs for Number/Name/Last name/Active/Unknown; everything else in the backend stays language-agnostic and leaves presentation to the frontend. Export writes a `Data` sheet (a single Excel Table named `Data`: Number, Name, Last name, Active, then categories alphabetical) and a `Metadata` sheet (one Table per category, sanitized to a valid Excel table name, values alphabetical plus an "Unknown"/"Onbekend" entry if not already present). Each category column on the Data sheet gets a list data-validation whose formula is a structured table reference (`TableName[ColumnName]`) into the Metadata table — this works cross-sheet even though a plain range reference wouldn't, confirmed by inspecting the generated `dataValidation`/`table` XML directly (ClosedXML's `IXLRange.CreateTable`/`CreateDataValidation().List(...)` write the formula string verbatim, no leading `=`). Import auto-detects language by checking which language's four fixed headers are all present, matches remaining headers to tenant category names, and reconciles rows against existing members **by federation number only** (match → update, no match/blank number → create); it never deletes members missing from the file. A category cell equal to the language's "Unknown"/"Onbekend" label (or blank, or naming a value that no longer exists) is treated as "no value" for that category, with a warning collected for the unrecognized case. Both endpoints require `CanManage` (Forbid otherwise) - export/import is a manager-or-higher action, same as the rest of this controller.
