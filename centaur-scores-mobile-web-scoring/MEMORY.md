# Project Memory

Written in the same spirit as [CLAUDE.md](CLAUDE.md) but focused on decisions/gotchas discovered while building specific features, rather than the stable architectural facts CLAUDE.md documents.

- **Scorecard signing (2026-09-20)** — see `../documentation/SIGNING-SCORECARDS.md` for the full cross-repo feature; this is the mobile-web-scoring client phase (API + web-ui + Flutter phases shipped first, in that order). `ScorekeeperMatch.signatureMode` (`'none' | 'confirm' | 'signature'`, new `SignatureMode` type) and `ScorekeeperMatchParticipant.signed`/`signedAtUtc`/`archerSignatureDataUrl`/`markerSignatureDataUrl` are new fields in `lib/types.ts`, mirroring the API response 1:1 like the rest of that file already does. New `SignRequest`/`PendingSignatures` types (`lib/types.ts`) parallel `PendingUpdates`/`PendingParticipantUpdates` but hold no "old" conflict-detection value, since signing has no conflict resolution per the spec.
- **Sync**: `lib/syncService.ts` gained `recordSignature`/`flushPendingSignatures`, structured exactly like `recordScoreEdit`/`flushPendingScores` (optimistic local apply → persisted `pendingSignatures` store → immediate flush attempt → picked up again by the same 8s retry timer used for scores) but without conflict handling - a `SCORECARD_SIGNED` `ApiError` from `postSign` is treated as success (the pending entry is dropped) rather than a failure to keep retrying, since that response means the end state (signed=true) is already correct (e.g. a raced duplicate send). Also needed a `signaturesSyncing` guard mirroring the existing `syncing` flag, for the same reason the Flutter client needed one — two `recordSignature` calls close together would otherwise both fire-and-forget overlapping flushes. `mergeMatchData` (`lib/matchService.ts`) gained a third parameter (`pendingSigned: PendingSignatures`) so a background poll re-applies a still-unsynced local signature the same way it already did for scores, and `initializeFromStartupParams` resets `pendingSignatures` alongside `pendingUpdates`/`matchData` on a fresh pairing (a new `?api=`).
- **`UpdateScoresAsync`'s existing conflict-entry shape gained a third `error` value it didn't have before: `SCORECARD_SIGNED`** (alongside `SCORE_CONFLICT`/`PARTICIPANT_CONFLICT`), returned when a queued score edit targets a participant whose card was signed (by this device or another) while the edit was still pending. `handleConflictResponse` needed a dedicated branch for it: unlike `SCORE_CONFLICT`, the entry's own `conflicts` array is always empty for this error, so treating it like a generic score conflict would have iterated an empty conflict-index set and silently dropped the pending edits as "applied fine" — actually wrong, since none of that participant's edits were applied at all. The fix drops every pending edit for that participant unconditionally (there's nothing left to apply, the card is permanently locked) and, unlike `PARTICIPANT_CONFLICT`, never surfaces it in `ConflictDialog` (there's no user decision to make - the read-only lock already prevents queuing further edits, and the next poll already reflects `signed: true`). Confirmed this is reachable in practice, not just theoretical: hitting `PUT .../scores` directly against an already-signed participant returns exactly this shape (`409 { error: { code: "UPDATE_SCORE_CONFLICT" }, conflicts: [{ error: "SCORECARD_SIGNED", conflicts: [] }] }`).
- **UI**: `components/SignArea.svelte` is a new persistent block rendered after `ScoreCardView`'s `{#each ends}` loop (sibling to the per-end blocks, inside the same `.view.score-card` div) - hidden entirely when `match.signatureMode === 'none'`, otherwise always showing either a "Sign" button, the recorded signature images, or a plain read-only notice (`confirm` mode, which never captures images). Tapping Sign opens `SignConfirmDialog.svelte` (`confirm` mode - a plain two-button dialog, structurally identical to the existing `ConflictDialog.svelte` overlay pattern) or `SignatureCaptureDialog.svelte` (`signature` mode - two stacked hand-rolled ink-capture `<canvas>` elements, `aspect-ratio: 5/1` each per the spec's split-screen sizing, using the exact same manual `pointerdown`/`pointermove`/`pointerup` tracking technique `ScoreCardView.svelte` already used for swipe gestures - no signature-pad package added, consistent with this repo's existing zero-runtime-dependency posture). Canvas state (per-pad `{drawing, lastX, lastY}`) is deliberately kept as a plain mutable object, not `$state`, since it's only read/written synchronously inside that pad's own pointer handlers and doesn't need to trigger re-renders - only `archerHasContent`/`markerHasContent` (gating the Confirm button and the "both required" error) are `$state`. Exports each pad via `canvas.toDataURL('image/png')` directly (no `RepaintBoundary`-equivalent needed, browsers already have this built into the Canvas API).
- **Read-only lock**: once `participant.signed`, `ScoreCardView`'s `onArrowTap`/`onKey`/`onDelete` all early-return, and the auto-focus `$effect` (which normally jumps to the first unscored arrow on entering a participant's card) treats a signed participant as "nothing to focus" regardless of `firstNullIndex`, so the keyboard never opens for them - there was no locked/read-only concept anywhere in this app before this feature, so this is new protection, not an extension of a pre-existing pattern. There is no anonymous unsign in this app (or in the API for anonymous callers at all) - withdrawing a signature is manager-only, via the authenticated full API, never exposed to a scoring device.
- **Scroll-to-sign-area**: reuses the exact same `scrollIntoView({block:'end', behavior:'smooth'})` technique the existing `$effect` already used for the on-screen keyboard, via a new `signAreaEl` binding + `scrollToSignArea()` helper. Triggered from two places: the existing "(re)activated for a participant" `$effect` (when the card is already complete on entry) and a new check at the end of `onKey()` (when the very last arrow of the whole card, not just the current end, is filled in while the view is already open - the existing `isLastArrowOfEnd` branch there only closed the keyboard, it never had a reason to scroll anywhere before this feature).
- **Verified live end-to-end (2026-09-20)**, unlike the Flutter client (whose `dart:io`-based HTTP layer can't run on web at all - see that repo's own MEMORY.md): started this app's real dev server plus the real API against the dev database, paired a live device URL for both `confirm` and `signature` mode test matches, and drove the full flow with Playwright including an actual mouse-drawn stroke on both canvases (`page.mouse.move/down/up`, which Chromium correctly turns into real pointer events) - confirmed the drawn strokes, the "both required" validation on an empty confirm attempt, the exported PNGs round-tripping through the API and back into the signed display, the read-only lock (tapping an arrow post-sign does not reopen the keyboard), and that a direct `PUT .../scores` against an already-signed participant returns the exact `SCORECARD_SIGNED` conflict shape `handleConflictResponse` above was written to handle. No console errors in any of it.
- **Bug: drawing a signature could swipe to a different participant mid-stroke (found via user report, fixed 2026-09-20).** `SignatureCaptureDialog`/`SignConfirmDialog` render as ordinary Svelte children of `SignArea`, which itself sits inside `ScoreCardView`'s `signAreaEl` div - a DOM *descendant* of the same `.view.score-card` div that owns the swipe-to-switch-participant pointer handlers (`onPointerDown`/`onPointerMove`/`onPointerUp` in `ScoreCardView.svelte`). `.overlay`'s `position: fixed` only detaches it visually; pointer events still bubble up the real DOM tree, so a signature stroke - a wide, fast horizontal drag on the canvas, exactly what `SWIPE_THRESHOLD`/`SWIPE_LOCK_THRESHOLD` are tuned to detect - reached the ancestor's swipe handler and called `switchToAdjacentParticipant()` while the dialog was still open, re-rendering it (still open, same dialog instance) bound to the *new* participant. The canvas strokes already drawn stayed, and confirming would attribute a signature to the wrong archer/marker. The Phase 2 live-verification pass above didn't catch this because its test match had only one participant, so the swipe silently no-op'd (no adjacent participant to switch to) - the bug only manifests with 2+ participants sharing a device, which is the normal real-world case. Fixed by adding `onpointerdown`/`onpointermove`/`onpointerup`/`onpointercancel={(event) => event.stopPropagation()}` directly on both dialogs' `.overlay` div (catches everything inside the dialog - canvas, buttons, blank space - rather than patching individual canvas handlers), leaving the existing per-canvas `event.preventDefault()` calls untouched (orthogonal - still needed to block the browser's native touch-scroll/back-gesture while drawing). Verified the fix is load-bearing, not coincidental: reverted it (`git stash` on just the two dialog files), re-ran a fresh two-participant Playwright regression test drawing a wide stroke mid-signature, and confirmed the dialog *did* silently rebind to the second participant ("Second Bowman" shown instead of "First Archer") without the fix, then confirmed it stays on the correct participant with the fix restored. Same root cause could in principle hit any future full-screen dialog rendered as a DOM descendant of `.score-card` rather than a sibling higher up the tree - the general fix pattern (stop propagation at the dialog's own overlay root) is the one to reach for again, not reworking the swipe handler itself.
